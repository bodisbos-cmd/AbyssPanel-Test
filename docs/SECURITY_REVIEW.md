# بررسی امنیتی Abyss Tunnel Panel

تاریخ بررسی: 2026-10-14  
دامنه بررسی: کد مخزن، تست‌های خودکار و مسیرهای API روی محیط CI؛ بدون دسترسی به داده‌ها یا اسرار محیط زنده Railway.

## کنترل‌های بررسی‌شده
- رمز مدیر با scrypt و salt مجزا هش می‌شود؛ رمز پیش‌فرض ثابت برای نصب جدید وجود ندارد.
- نشست مدیر با کوکی امضاشده، SameSite=Strict و Secure در محیط HTTPS استفاده می‌شود.
- عملیات تغییردهنده داشبورد به CSRF token نیاز دارد.
- ورود دارای محدودیت تلاش است؛ مسیرهای API ربات نیز محدودیت نرخ دارند.
- کلید API به‌صورت تصادفی ساخته می‌شود، فقط هش SHA-256 آن ذخیره می‌شود و کلید خام تنها یک بار نمایش داده می‌شود.
- مجوزهای API جدا هستند: مشاهده مشتریان، تغییر مشتریان و دریافت لینک اشتراک.
- شناسه‌ها و نام‌ها اعتبارسنجی می‌شوند و محتوای HTML در صفحات مدیریتی/اشتراک escape می‌شود.
- فایل بکاپ در زمان بازیابی از نظر ZIP، حجم، نسبت فشرده‌سازی، صحت SQLite و وجود جداول اصلی بررسی می‌شود.
- اگر اعمال تنظیمات یا تغییرات Xray شکست بخورد، تلاش برای rollback انجام می‌شود.
- دیتابیس، فایل رمز اولیه و کلید نشست در مسیر پایدار /data قرار می‌گیرند؛ اسرار در README قرار داده نشده‌اند.

## تست‌های خودکار اضافه‌شده
- API بدون کلید، کلید لغوشده و مجوز ناکافی را رد می‌کند.
- ساخت، فهرست، توقف و حذف مشتری از API بررسی می‌شود.
- دسترسی مدیریتی به پایش و مدیریت کلیدها بررسی می‌شود.
- بکاپ ZIP دریافت و بازیابی می‌شود؛ فایل نامعتبر رد می‌شود.
- صفحه اشتراک، راهنما، لینک‌های رسمی دانلود و مسیر عیب‌یابی بررسی می‌شوند.
- پیکربندی Xray و مسیرهای HTTP مربوط به پروفایل‌ها در CI بررسی می‌شوند.

## محدودیت‌ها و ریسک‌های باز
- این سند گواهی تست نفوذ مستقل نیست. هنوز تست نفوذ خارجی و بررسی دستی توسط متخصص ثالث انجام نشده است.
- تست CI نمی‌تواند اتصال واقعی از اپراتورهای مختلف، پینگ تونل، سرعت دانلود/آپلود یا سازگاری همه نسخه‌های برنامه‌ها را ثابت کند.
- کلیدهای API و لینک‌های اشتراک را اطلاعات حساس فرض کن؛ دسترسی به فایل بکاپ نیز باید محدود باشد.
- API فعلی برای یک مدیر اصلی طراحی شده و نقش‌های چندمدیره/سطوح دسترسی انسانی هنوز پیاده‌سازی نشده‌اند.
- اندازه‌گیری سرعت در داشبورد، تغییر مصرف ثبت‌شده را نشان می‌دهد؛ تست سرعت اینترنت و پینگ واقعی کاربر نیست.
- پروفایل‌های XHTTP جدید باید پس از استقرار آزمایشی با کلاینت واقعی روی شبکه‌های هدف سنجیده شوند.

## چک‌لیست پیش از فروش عمومی
1. رمز مدیر را عوض کن و بکاپ را بیرون از Railway ذخیره کن.
2. کلید API اختصاصی ربات بساز و فقط مجوزهای لازم را بده.
3. لینک اشتراک را در کانال عمومی یا گزارش خطا قرار نده.
4. بازیابی بکاپ را روی سرویس آزمایشی با داده غیرواقعی تمرین کن.
5. اتصال واقعی WS، HTTPUpgrade و تمام حالت‌های XHTTP را با حداقل دو کلاینت و شبکه‌های هدف بررسی کن.
6. پیش از اعلام پینگ/سرعت، از همان دستگاه و اپراتور تست بگیر.
